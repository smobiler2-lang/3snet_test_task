# Code review модуля Deletion

## Коротко

Идея модуля хорошая: описывать зависимости прямо на сущностях через attribute и иметь один общий сервис, который перед удалением показывает, что будет затронуто. Для большой системы это полезно: меньше случайных удалений, понятнее UX, проще добавить логирование или метрики.

Но текущая реализация выглядит как рабочий черновик, который еще нужно укрепить перед использованием в проде. Основные риски: много неявной логики, слабая валидация правил, возможные проблемы на больших объемах данных и несколько мест, где код может тихо сделать не то.

## Что сделано хорошо

- Есть понятная точка входа: `DeletionService::canDelete()` для простой проверки и `analyze()` для более подробного результата.
- Зависимости описываются декларативно через `RelationTo`, это лучше, чем держать отдельный ручной список связей.
- Есть разделение между анализом (`DeletionService`) и выполнением удаления (`DeletionOrchestrator`).
- Есть middleware-интерфейс. Это хорошее место для логов, аудита, метрик и интеграций.
- DTO простые и читаемые, без лишней логики.

## Что я бы поправил в первую очередь

1. `README.md` расходится с кодом.

В документации написано про `DependsOn`, `parent`, `hard`, но в коде используется `RelationTo`, `entity`, `type`, `cascade`. Еще в примере сказано, что `OrderItemEntity` нельзя удалить, если она связана с `OrderEntity`, а в коде наоборот: `BLOCKING` на ребенке блокирует удаление родителя. Это легко запутает следующего разработчика.

2. `supports()` у middleware сейчас не работает.

В `DeletionMiddlewareInterface` есть метод `supports(string $entityClass)`, но `DeletionOrchestrator::notify()` его не проверяет. Значит любой middleware будет получать все события, даже если сам говорит, что не поддерживает этот класс.

3. Ошибки middleware полностью проглатываются.

В `notify()` ловится любой `Throwable` и ничего с ним не делается. Для логирования это еще можно пережить, но для аудита или метрик это опасно: операция выглядит успешной, хотя важная побочная логика могла сломаться.

4. Нет защиты от циклов в каскадном плане.

`DeletionOrchestrator` рекурсивно строит план удаления. Если в правилах появится цикл между сущностями, можно получить бесконечную рекурсию или очень тяжелый обход. Нужен visited-set по паре `class + id`.

5. Есть риск N+1 запросов.

При построении плана код по одному загружает дочерние сущности через repository. На больших данных это быстро станет проблемой. Лучше строить план пачками и ограничивать глубину/размер результата.

6. Join table обрабатывается неодинаково.

В одном месте используется Doctrine QueryBuilder с `from($joinTable, 'jt')`, в другом месте raw SQL. Если `joinTable` это реальная таблица, DQL QueryBuilder здесь может быть неправильным инструментом. Для join table я бы использовал DBAL QueryBuilder.

7. Raw SQL собирает имена таблиц и колонок через `sprintf`.

Значения приходят из attributes, то есть из кода, а не от пользователя. Но все равно лучше валидировать имена таблиц/колонок или брать их из Doctrine metadata. Так меньше шансов получить ошибку из-за опечатки или нестандартного имени.

8. `dryRun` выглядит неоднозначно.

При `dryRun=true` удаления не происходит, но `afterDetachRelations`, `afterDeleteChildren`, `afterDeleteRoot` все равно вызываются. По названию `after*` кажется, что действие реально произошло. Я бы добавил отдельный флаг в событие или отдельные dry-run события.

## Потенциальные баги и edge cases

- Составной primary key почти не поддержан. В нескольких местах берется первый identifier или предполагается поле `id`.
- `getScalarFkValue()` читает поле через reflection и ожидает scalar id, но поле может быть Doctrine association object.
- JSON ids фильтруются через `array_filter()`, из-за этого ключи массива сохраняются. Лучше вернуть `array_values(...)`.
- Для JSON поля строка с невалидным JSON просто превращается в пустую зависимость. Возможно, лучше явно логировать или бросать доменное исключение.
- `count($ids)` может считать дубли. Если репозиторий вернет повторяющиеся id, результат будет завышен.
- `deleteByIds()` делает bulk delete через DQL. Это обходит lifecycle callbacks Doctrine и может не сработать так, как ожидают сущности с событиями.
- Нет лимита на количество ids в `IN (:ids)`. На больших списках можно упереться в лимиты БД или получить тяжелый запрос.
- Если объект еще не сохранен и у него нет id, поведение не определено.

## Архитектура и SOLID

Главная проблема в том, что `DeletionService` знает слишком много: attributes, reflection, Doctrine metadata, JSON, join table, поиск детей и сбор DTO. Я бы постепенно разделил это на несколько частей:

- `RelationRuleProvider` - читает attributes и строит правила.
- `RelationResolver` - ищет зависимости по конкретному правилу.
- `DeletionAnalyzer` - собирает итоговый `RelationsDto`.
- `DeletionPlanner` - строит план удаления.

Так код будет проще тестировать и менять. Например, JSON-связи и join table можно будет проверять отдельно.

## Symfony / Doctrine best practices

- Для Symfony лучше явно описать регистрацию middleware через tagged iterator.
- Если middleware имеет `supports()`, orchestrator должен его учитывать.
- Для join table лучше использовать DBAL, а не DQL.
- Для bulk delete нужно явно решить, допустимо ли обходить Doctrine lifecycle events.
- Хорошо бы добавить свои exception-классы: например, для неправильного attribute, неподдержанного типа связи или отсутствующего id.

## Что бы я сделал дальше

Сначала я бы поправил документацию и контракт поведения: что именно значит `BLOCKING`, когда работает `cascade`, что возвращает `canDelete`. Потом добавил бы тесты на базовые сценарии: blocking child, reference child, detach relation, delete cascade, JSON field, отсутствие id, циклическая связь.

После этого уже можно усиливать реализацию: валидация правил, visited-set в рекурсии, batch-запросы и нормальная обработка ошибок middleware.

## Реализация части 2

Для практической части я выбрал вариант B: `MetricsDeletionMiddleware`.

Что измеряется:

- количество batch-операций detach;
- количество строк, затронутых detach;
- длительность detach;
- количество batch-операций удаления детей;
- количество удаляемых дочерних строк;
- длительность удаления детей;
- старт и успешное завершение удаления root-сущности;
- длительность удаления root-сущности.

В labels я намеренно не добавлял id сущностей. Для метрик это плохая идея: будет слишком высокая кардинальность. Оставлены только классы сущностей, стадия операции и имя join table.
